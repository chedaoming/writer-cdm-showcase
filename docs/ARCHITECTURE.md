# 架构说明

## 1. 数据流

```
选题 TopicCandidate
   ↓ 蓝图 BlueprintPlan（世界观、人物、分章节点、呼吸点密度）
   ↓ 知识库注入（按题材/子类/工序过滤规则）
   ↓ 上下文构建 ContextPackage（分层历史 + 当前步骤字段 + 预算裁剪）
   ↓ 生成 Writing（分段落产出，断点续跑）
   ↓ 评审 AuditReport（六维评分）
   ↓ 修订 RevisionRound（按短板定向修复，最多 N 轮，分数不升即停）
   ↓ 导出（知乎盐选等平台格式适配 + 合规检查）
```

## 2. 上下文构建

长文本失败的主因不是模型不够大，而是上下文里塞了太多无关信息。项目按「步骤 → 字段策略」的方式组织上下文：

- `FIELD_POLICIES`：声明每个工序需要哪些字段、优先级与截断策略。
- 分层历史：最近章节全文、较早章节摘要、角色卡与设定表常驻。
- token 预算：先生成骨架再填充细节，超预算时优先保留设定与当前步骤指令。

## 3. 六维评分

| 维度 | 代码侧信号 | LLM 侧职责 |
| --- | --- | --- |
| 逻辑 logic | 段落衔接率、时间锚点、因果链 | 判定因果关系是否成立 |
| 情绪 emotion | 感官细节密度、禁用词命中 | 判断情绪是否真实而非堆叠 |
| 人味 humanity | 语气词、口语化、对话密度 | 判断是否像人写的 |
| 反转 twist | 悬念引入/回收率、反转标记 | 判断反转是否有效 |
| 角色 character | 称呼一致性、台词区分度 | 判断角色弧光是否成立 |
| 节奏 rhythm | 句长变异系数、短长交替、对话比 | 判断阅读节奏 |

混合策略：代码为主时稳定但区分度低；LLM 为主时有区分度但波动大。实际配置为按维度分配权重（例如逻辑与情绪以 LLM 为主、人味以代码为主），并在 LLM 调用失败时自动降级为纯代码评分，保证流水线不中断。

## 4. 校准方法

1. 选取同题材样本集（数十篇），先人工给出 1—10 分基准。
2. 用两套模型分别打分，计算 Pearson r 与 MAE。
3. 同一模型重复运行两次，测自一致性，估算评分任务的上限。
4. 根据结果调整权重、提示词（temperature=0、先评语后打分、拉大分数区间）。

关键结论：评分任务本身的天花板约 r≈0.3，所以产品上不承诺「模型替你判断好坏」，只提供「相对排序 + 短板定位 + 可执行修改建议」。

## 5. 工程化护栏

- **断点续跑**：按段落保存进度，失败重跑不重复消耗配额。
- **模型降级**：主模型重试失败后切换备用模型，并记录降级事件。
- **预算控制**：单章 token 上限、单次运行总预算、配额耗尽提前终止。
- **静默失败治理**：关键路径的 catch 必须带结构化日志，禁止无声吞异常。
- **测试**：约 490 项单元测试，覆盖上下文压缩、规则过滤、评分计算、API 路由与错误分支。

## 6. 已知短板

- 节奏维度的代码化度量仍有争议，LLM 判定不稳定。
- 长链路多 Agent 的任务编排成本高，单章生成依赖外部模型配额。
- 知识库质量依赖拆书管线的输入质量，存在规则互相冲突的情况，需要冲突检测。
